# Agile, Scrum, XP, and Lean/Kanban

Scrum, XP, and Lean/Kanban may seem different, but all of them are inspired by the **Agile Manifesto**.

The Agile Manifesto defines:

- **4 Core Values**
    
- **12 Principles**
    

These values and principles guide how teams should work in different environments.

## Different Agile Approaches

### **Scrum → Project Management**

Focuses on:

- What work is getting done
    
- Prioritizing tasks
    
- Ensuring work aligns with user and stakeholder needs
    

### **XP (Extreme Programming) → Software Development**

Focuses on:

- High-quality code
    
- Good design and architecture
    
- Maintainable and testable software
    

### **Lean/Kanban → Process Improvement**

Focuses on:

- Improving how teams build software
    
- Reducing waste
    
- Increasing workflow efficiency
    

## Simple Example

Think of a restaurant:

- **Scrum** manages customer orders and delivery timing
    
- **XP** ensures food quality and cooking standards
    
- **Kanban/Lean** improves kitchen workflow and removes waste
    

Different focus areas and practices are what make them different.

# Lean Mindset

Lean focuses on:

- Reducing waste
    
- Delivering only what adds value
    
- Focusing on essentials
    

# 8 Wastes of Lean (with IT Examples)

|Waste|Example in IT|
|---|---|
|**Transport**|Moving project files repeatedly between multiple tools instead of using a centralized repository like GitHub|
|**Inventory**|Keeping a large backlog of untested code branches waiting for deployment|
|**Motion**|Developers wasting time switching between many dashboards, chats, and monitoring tools|
|**Waiting**|QA testers waiting for delayed build approvals before starting testing|
|**Overproduction**|Developing features users never requested or use|
|**Over-processing**|Creating excessive documentation for small code changes|
|**Defects**|Bugs in production causing repeated hotfixes and customer complaints|
|**Non-Utilized Talent**|Skilled engineers spending most of their time on manual data entry instead of innovation|

# What is Kanban?

**Kanban** is a simple work management method that visually tracks tasks using stages like:

> **To Do → In Progress → Done**

It helps teams:

- Visualize work
    
- Limit overload
    
- Improve efficiency
    
- Maintain continuous workflow
    

Kanban is designed to support a **continuous and steady flow of work**.

# Scrum vs Kanban

|Feature|Scrum|Kanban|
|---|---|---|
|**Work Style**|Fixed time-based sprints|Continuous workflow|
|**Planning**|Planned at the start of each sprint|Tasks added anytime|
|**Roles**|Scrum Master, Product Owner, Development Team|No mandatory roles|
|**Task Board**|Sprint board resets every sprint|Board is continuous|
|**Changes During Work**|Changes avoided during sprint|Changes allowed anytime|
|**Best For**|Planned product development|Ongoing support and maintenance|
|**Focus**|Delivering sprint goals|Improving flow and reducing bottlenecks|
|**Meetings**|Daily standups, sprint review, retrospectives|Fewer mandatory meetings|

## Simple Examples

- **Scrum:** A software team releases features every 2 weeks in planned batches.
    
- **Kanban:** An IT support team continuously handles tickets as they arrive.
    

# 6 Core Principles of Kanban

1. **Visualize the Workflow**  
    Use a board to track all tasks and their status.
    
2. **Limit Work in Progress (WIP)**  
    Avoid handling too many tasks simultaneously.
    
3. **Manage Flow**  
    Ensure work moves smoothly without bottlenecks.
    
4. **Make Process Policies Explicit**  
    Clearly define how work should be done.
    
5. **Implement Feedback Loops**  
    Regularly review and improve the process.
    
6. **Improve Collaboratively and Evolve Experimentally**  
    Continuously improve through teamwork and small incremental changes.
    

# Push vs Pull System in Kanban

|System|Meaning|Example in IT|
|---|---|---|
|**Push System**|Work is assigned regardless of team capacity|A manager assigns 10 tasks to a developer at once|
|**Pull System**|Team members pull work only when ready|A developer picks the next ticket after completing the current one|

## Simple Difference

- **Push System** → Work is forced onto people
    
- **Pull System** → People take work when they are ready
    

Kanban mainly follows the **Pull System** to:

- Avoid overload
    
- Improve workflow
    
- Maintain steady delivery pace

# Cycle Time vs Lead Time

|Term|Meaning|Example|
|---|---|---|
|**Lead Time**|Total time from request to delivery|Customer raises a feature request on Monday, and it is delivered on Friday → **5 days lead time**|
|**Cycle Time**|Time taken to actively work on the task|Developers actually worked on it from Wednesday to Friday → **3 days cycle time**|

## Simple Difference

- **Lead Time** = Waiting time + Working time
    
- **Cycle Time** = Only actual working time
